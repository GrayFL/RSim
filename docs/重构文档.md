# RSim Component / Signal 架构重构说明

## 1. 重构目标

当前 RSim 以 `Sensor` 为核心抽象。`Sensor` 同时承担了两类职责：

* **运行职责**：生命周期、依赖关系、Task、WatchDog、失败传播、进程边界；
* **数据职责**：`Frame`、`get()`、history、时间戳查询、latest-value 语义。

这种设计在传感器组合阶段非常简洁：

```text
Sensor -> Map -> Bundle -> ProcessSensor
```

但当系统扩展到 SLAM、Navigation、控制器、底盘等复杂组件后会产生矛盾：

* 中间计算结果仍然需要 `get()`、history、时间查询和多消费者；
* 一个组件往往有多个输入和多个输出，无法自然定义单一 `get()`；
* 控制输出需要连接执行器，但不应该因此重新构造计算组件；
* 生命周期层级与数据依赖关系并不一致；
* 跨进程 / DDS / shared-memory 应由部署位置决定，而不应由逻辑组件层级决定。

因此重构目标是把原来的 `Sensor` 拆成两个正交概念：

```text
原 Sensor
   │
   ├── Component    负责计算与生命周期
   └── Signal       负责时间序列数据
```

核心原则：

> **Component 描述“谁在运行”，Signal 描述“什么数据在流动”。**

---

# 2. 核心抽象

## 2.1 Component

`Component` 是运行和生命周期单位。

负责：

```text
dependencies
open / close
task
WatchDog
failure propagation
placement
process supervision
resource ownership
```

概念接口：

```python
class Component:
    dependencies: tuple[Component, ...]

    async def open(self): ...
    async def close(self): ...

    def task(self, name, callback, *, hz): ...
```

复杂软件模块和物理设备统一属于 Component：

```text
Camera
Lidar
Chassis
SLAM
Navigation
Controller
Recorder
Map
Bundle
Synchronizer
```

Component 本身不要求具有 `get()` 或 `set()`。

---

## 2.2 Signal[T]

`Signal[T]` 表示一个带时间语义的可读取数据源。

它继承当前 `Sensor` 中最有价值的数据语义：

```python
frame = await signal.get()

frame = await signal.get(
    after=previous.sequence
)

frame = await signal.get(
    timestamp_ns=t,
    clock="robot",
    tolerance_ns=...
)
```

Signal 负责：

```text
Frame
history
sequence
latest-value
timestamp lookup
wait for next value
```

Signal 本身没有独立生命周期。

它由某个 Component 产生：

```text
Component
    │
    │ produces
    ▼
Signal[T]
```

因此：

> 中间计算结果可以是 Signal，但不会因此产生额外生命周期节点。

---

## 2.3 Frame[T]

保留现有模型：

```python
@dataclass(frozen=True)
class Frame(Generic[T]):
    data: T
    stamp_ns: int
    clock: str
    received_ns: int
    sequence: int
```

其中 `sequence` 定义为：

> 当前 Signal 内部的本地观察顺序。

未来如需要跨进程、跨设备稳定识别同一次物理采样，可以增加：

```text
source_id
source_epoch
sample_id
```

但不应改变 `sequence` 的本地 cursor 语义。

# 3. 数据流图和生命周期图分离

这是本次重构最核心的原则。

## 生命周期图

描述 Component 之间的运行依赖：

```text
RobotApplication
├── Camera
├── Lidar
├── SLAM
├── Navigation
└── Chassis
```

解决：

```text
谁启动
谁停止
谁拥有进程
谁的失败向谁传播
谁需要监督
```

---

## 数据流图

描述 Signal 之间的生产和消费：

```text
camera.image ─────┐
lidar.points ─────┼──> SLAM ──> slam.pose ─────┐
imu.data ─────────┤                             │
odom ─────────────┘                             ├──> Navigation
                                                │
local_cloud ────────────────────────────────────┘
                                                     │
                                                     ▼
                                             nav.velocity_command
                                                     │
                                                     ▼
                                               chassis.velocity
```

两张图不要求同构。

原则：

> **Ownership 是树或 DAG，Dataflow 是任意有向图。**

# 4. Component 可以暴露多个 Signal

复杂 Component 不需要一个模糊的 `get()`。

例如：

```python
class SLAM(Component):
    pose: Signal[Pose]
    map: Signal[Map]
    keyframes: Signal[Keyframes]
```

使用：

```python
pose = await slam.pose.get()
map_frame = await slam.map.get()
```

Navigation：

```python
class Navigation(Component):
    global_path: Signal[Path]
    local_path: Signal[Path]
    velocity_command: Signal[VelocityCommand]
```

底盘：

```python
class Chassis(Component):
    odom: Signal[Odometry]
    state: Signal[ChassisState]
    velocity: CommandSink[VelocityCommand]
```

这样物理设备、算法模块、控制模块都能采用同一种 Component 模型。

---

# 5. 简单组件可以保留 get() 快捷接口

为了兼容当前 RSim 的易用性，可以允许：

> 有唯一 primary output 的 Component 提供 `get()` shortcut。

例如 Camera：

```python
camera.image
```

同时：

```python
await camera.get()
```

等价于：

```python
await camera.image.get()
```

Map：

```python
mapped.output
```

同时继续允许：

```python
await mapped.get()
```

但对于：

```text
SLAM
Navigation
Chassis
```

这类多输出 Component，不应强行定义一个含义模糊的 `get()`。

---

# 6. Map 和 Bundle 的新语义

## Map

当前：

```python
mapped = Map(source, function)
```

重构后逻辑上变成：

```text
             Map Component
Signal[A] ─────────────────> Signal[B]
```

概念实现：

```python
class Map(Component):
    def __init__(self, source, function):
        self.source = source
        self.output = Signal()

    async def transform(self):
        frame = await self.source.get(after=self.previous)

        value = self.function(frame.data)

        await self.output.publish(
            value,
            stamp_ns=frame.stamp_ns,
            clock=frame.clock,
            received_ns=frame.received_ns,
        )
```

为了兼容：

```python
await mapped.get()
```

可以代理至：

```python
await mapped.output.get()
```

---

## Bundle

Bundle 保持“latest snapshot”语义：

```text
Signal[A] ─┐
           ├── Bundle Component ──> Signal[Bundle]
Signal[B] ─┘
```

Bundle 不负责严格时间同步。

---

# 7. Synchronizer / TimeJoin

复杂机器人组件需要将时间同步正式提升为框架能力。

例如 SLAM：

```python
sync = Synchronizer(
    image=camera.image,
    cloud=lidar.points,
    imu=imu.data,
    odom=chassis.odom,
    tolerance_ns=20_000_000,
)
```

输出：

```text
Signal[SynchronizedSamples]
```

例如：

```text
                     reference t
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
 image nearest      imu interpolate    odom interpolate
```

Synchronizer 与 Bundle 的区别：

```text
Bundle
    各输入 latest value

Synchronizer
    对同一逻辑时间进行 Join
```

---

# 8. Clock / TimeDomain

当前 `Frame.clock: str` 的设计应保留，并进一步正式化。

不同来源可能有：

```text
camera_hw
lidar_hw
imu_hw
robot_time
unix
simulation_time
```

框架原则：

> 不同 Clock Domain 的 timestamp 默认不可直接比较。

可以逐步增加：

```text
ClockDomain
ClockTransform
```

例如：

```text
camera_hw ─┐
lidar_hw ──┼──> robot_time
imu_hw ────┘
```

Synchronizer 只应：

* 接收同一 Clock Domain 的 Signal；
* 或要求显式存在 ClockTransform。

不应由 SLAM / Navigation 自己隐式假设设备时间可以直接比较。

---

# 9. 多消费者

Signal 天然允许 fan-out。

例如 SLAM pose：

```text
                     ┌── Navigation
                     │
slam.pose Signal ────┼── UI
                     │
                     ├── Recorder
                     │
                     └── Debugger
```

只有一个 producer：

```text
SLAM
```

消费者数量不影响 producer 是否重新计算。

同进程：

```text
直接引用同一个 Frame / payload
```

跨进程：

```text
一次 SharedStore materialization
          │
          ├── Consumer A mmap
          ├── Consumer B mmap
          └── Consumer C mmap
```

因此：

> **逻辑 fan-out 不等于物理数据复制。**

---

# 10. 控制输出也是 Signal

Navigation 不应该直接调用底盘。

推荐：

```text
Navigation
     │
     ▼
Signal[VelocityCommand]
     │
     ▼
Chassis.velocity
```

Navigation 输出：

```python
nav.velocity_command
```

既可以：

```python
cmd = await nav.velocity_command.get()
```

用于调试，也可以连接到真实执行器。

这样 Navigation 可以脱离真实底盘运行：

```text
Navigation
    │
    ├── Real Chassis
    ├── Simulator
    ├── Recorder
    └── Visualization
```

---

# 11. CommandSink / Actuator

写方向定义独立接口：

```python
class CommandSink(Generic[T]):
    async def set(self, command: T): ...
```

例如：

```python
await chassis.velocity.set(
    VelocityCommand(
        linear_x=0.5,
        angular_z=0.1,
    )
)
```

`CommandSink` 不需要 `get()`。

如果需要反馈，应作为单独 Signal：

```text
chassis.velocity_command   CommandSink
chassis.velocity_feedback  Signal
```

---

# 12. Signal 到 Actuator 的连接

通过显式 Component：

```python
drive = Connect(
    nav.velocity_command,
    chassis.velocity,
)
```

逻辑：

```text
Signal[T]
    │
    ▼
 Connect
    │
    ▼
Sink[T]
```

内部：

```python
frame = await source.get(after=previous)
await sink.set(frame.data)
```

因此：

```text
nav.velocity_command
        │
        ├── Debug UI
        ├── Recorder
        └── Connect → chassis.velocity
```

不需要重新运行 Navigation。

---

# 13. 多控一：CommandMux / Arbiter

Sensor/Signal 多读天然安全，但 Actuator 多写必须显式仲裁。

例如：

```text
Navigation ─────┐
                │
Joystick ───────┼──> CommandMux ──> chassis.velocity
                │
EmergencyStop ──┘
```

而不是：

```text
Navigation ──┐
Joystick ────┼──> chassis.velocity
Safety ──────┘
```

`CommandMux` 可以实现：

```text
priority
manual override
exclusive ownership
timeout
fallback
```

例如：

```text
EmergencyStop  priority 100
Joystick       priority 50
Navigation     priority 10
```

控制仲裁属于应用语义，不应依赖 DDS “最后到达的数据”。

---

# 14. Command TTL / Deadman

实时执行器尤其是底盘应支持：

```text
command deadline
controller epoch
sequence
```

例如：

```python
VelocityCommandEnvelope(
    value=VelocityCommand(...),
    controller_id=...,
    controller_epoch=...,
    sequence=...,
    deadline_ns=...,
)
```

Provider 端负责：

```text
command valid
    → apply

command expired
    → safe state / stop
```

这样即使：

```text
应用崩溃
DDS 断开
网络中断
控制循环卡死
```

硬件侧仍能进入安全状态。

---

# 15. Placement 与数据流解耦

Signal 只是逻辑边，不应该自动对应：

```text
DDS topic
共享内存文件
```

例如：

```text
Component A
    │
 Signal X
    │
Component B
```

如果同进程：

```text
Signal X
    → Python reference
```

不需要共享内存。

如果跨进程：

```text
Signal X
    → SharedStore
    → descriptor DDS
    → mmap
```

如果未来跨机器：

```text
Signal X
    → network payload transport
```

因此：

> **Transport boundary 由 placement 决定，而不是由 Component boundary 决定。**

---

# 16. DDS 的角色

DDS 应从：

```text
“Sensor 的传输协议”
```

逐渐演化成：

```text
“跨 placement boundary 的 Signal transport”
```

结构：

```text
Logical Signal
      │
      ▼
Channel Binding
      │
      ├── LocalReference
      ├── SharedMemoryChannel
      └── DDSChannel
```

现有：

```text
DDS descriptor + SharedStore
```

可以继续作为同 host 跨进程实现。

上层 Signal API 不改变。

---

# 17. 物理数据与逻辑 Signal 解耦

Signal 只代表逻辑数据。

例如：

```text
slam.local_map
```

并不意味着一定有一个新的物理 buffer。

同进程：

```text
Frame -> existing ndarray
```

跨进程才 materialize：

```text
Signal
   ↓
SharedStore
   ↓
inode X
   ├── mmap consumer A
   └── mmap consumer B
```

所以：

```text
Signal identity
≠
payload identity
≠
Component identity
```

应继续保持当前 RSim 已经形成的物理数据共享机制。

# 20. Runtime 的新职责

Runtime 不再仅解析 Sensor DAG，而解析：

```text
Component Graph
+
Signal Dependencies
+
Placement
```

每个 Signal 知道：

```text
producer Component
```

因此：

```python
Runtime(slam.pose)
```

可以反向解析：

```text
slam.pose
   ↓ producer
SLAM
   ↓ inputs
Synchronizer
   ↓ inputs
Camera / Lidar / IMU / Chassis
```

从请求的 output 自动得到所需 Component 集合。

这可以逐渐替代手工维护完整生命周期树。

# 23. 重构后需要保持的核心不变量

1. **Component 是生命周期单位，不是数据值。**

2. **Signal 是时间序列数据单位，没有独立资源生命周期。**

3. **一个 Component 可以产生多个 Signal。**

4. **一个 Signal 可以有任意数量消费者。**

5. **逻辑 fan-out 不应导致重复计算。**

6. **逻辑 Component 边界不应自动导致数据复制。**

7. **只有 placement boundary 才决定 IPC / DDS / shared-memory。**

8. **不同 Clock Domain 默认不能直接同步。**

9. **Bundle 表示 latest snapshot，Synchronizer 表示 time join。**

10. **Actuator 多写必须显式仲裁，不能依赖 middleware 最后写入者。**

11. **控制超时与安全停止应发生在最靠近硬件的 Provider。**

12. **ROS1 / ROS2 / DDS / mmap 都属于 adapter / transport 层，不进入 Component 和 Signal 的核心语义。**

---

# 24. 最终模型

重构后的 RSim 可以概括为：

```text
                         RSim Runtime

                 ┌───────────────────────┐
                 │      Component        │
                 │ computation/lifetime  │
                 └───────────┬───────────┘
                             │ produces
                             ▼
                 ┌───────────────────────┐
                 │       Signal[T]       │
                 │ time-indexed data     │
                 └───────────┬───────────┘
                             │
                  dataflow / fan-out
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
        Component input                CommandSink
                                            │
                                            ▼
                                         Hardware

Placement 决定 Signal 的物理实现：

same process
    → direct reference

cross process / same host
    → SharedStore + mmap + DDS descriptor

cross host
    → DDS / future network payload transport
```

最终核心思想可以浓缩成一句话：

> **Component 构成运行图，Signal 构成数据图，Frame 提供时间语义，Transport 负责把逻辑 Signal 映射到实际通信机制。**

这使 RSim 从“可组合 Sensor Runtime”自然演化为一个适用于传感器、SLAM、导航、控制和跨设备通信的 **Component / Signal Runtime**。
