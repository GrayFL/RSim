## 1. 目标与边界

### 1.1 本次要完成什么

将已经实现的 Windows 支持收敛为可维护的平台适配层；用共同的运行时状态机管理 Linux 和 Windows；通过契约测试证明真实硬件与仿真能够复用上层程序。

基线已经具备 Windows Job Object、loopback 本地连接、NPY 文件映射以及 MuJoCo Component。**本次不重写这些实现，而是隔离平台差异、补齐失败与回收契约、建立持续验证。**[R1][R2]

核心决策如下。

| 编号 | 决策 |
|---|---|
| D1 | 保持 `Component / Signal / Frame / CommandSink` 的基本含义和现有调用方式 |
| D2 | `Runtime` 决定生命周期与需求；平台层只提供操作系统原语，不决定业务策略 |
| D3 | `ProcessPlacement` 跟随所属 Runtime；共享 provider 跟随所有源租约，不跟随第一个创建者 |
| D4 | 平台原语放入独立 `rsim.platforms` 包，供 runtime 与 transport 使用，避免反向依赖 |
| D5 | 同机跨进程仍用 DDS 描述信息＋只读文件映射；不因 Windows 支持而改为消息内嵌大数组 |
| D6 | 端口需求采用独立状态，不再由 `_prepare_hooks` 推断；昂贵采样可显式响应需求 |
| D7 | 相同场景跨后端验证数据含义与安全行为，不要求真机和仿真逐位一致 |
| D8 | 不满足必要能力时启动失败，不静默退化为 `inprocess`、无监督进程或无期限控制 |、

## 2. 支持矩阵：先定义承诺，再做适配

以下是**目标验收范围**，不是“所有组合已经通过”的声明。

| 场景 | Linux | Windows 10/11＋本地 NTFS | 本次约束 |
|---|---|---|---|
| 本进程 Component / Signal | 必测 | 必测 | 不加载 ROS 或 DDS 也能运行纯计算 |
| `inprocess` 描述信息总线 | 必测 | 必测 | 仅同一进程／事件循环，不替代真实 DDS 测试
| `ProcessPlacement` | 必测 | 必测 | 同一 Python 环境，真实子进程，明确监督 |
| `SharedProvider / SharedComponent` | 必测 | 必测 | 同机、同用户、兼容协议与存储命名空间 |
| 独立 Python 环境互通 | 必测 | 必测 | 在明确选定的解释器组合上验证；不跨环境传工厂 |
| MuJoCo 物理、无 RGBD | 必测 | 必测 | 使用程序生成的小场景，不依赖私有素材 |
| MuJoCo RGBD | 指定渲染环境必测 | 指定渲染环境必测 | 图形能力单独验收，headless 不代表无需渲染支持 |
| 原生 ROS2 硬件／建图 provider | 指定 Linux 环境验收 | 不作统一承诺 | Windows 可以是客户端，不要求具备全部 provider 依赖 |
| Linux ↔ Windows 控制小消息 | 独立集成测试 | 独立集成测试 | 通过既有 DDS 控制服务，不通过本地注册表 |
| Linux ↔ Windows 通用 mmap 数据 | 不支持 | 不支持 | 相同文件路径或同一物理电脑也不构成共享契约 |

**WSL 按 Linux 执行环境处理，不能把 Windows 原生进程与 WSL 进程当作同一个 RSim 共享存储域。** 它们之间采用已支持的网络接口；不通过挂载盘路径绕过 host/boot/存储域校验。容器同理：只有明确共享了注册表、权限和存储命名空间，并通过验证，才视为同一共享域。

macOS 不在本次多进程发布门禁内；不能因为 `os.name != 'nt'` 就走 Linux 的 `/proc`、`prctl` 或 `/dev/shm` 实现。未知平台在请求不支持的能力时返回明确错误。

## 3. 对外 API：稳定主要入口，只增加少量配置与诊断

### 3.1 保持不变的接口

```python
# 现有调用方式继续成立。
from rsim import Runtime, Map, ProcessPlacement
from rsim.components.synthetic import CounterArray

async def example():
    source = CounterArray(size=1024)
    squared = Map(source.output, lambda x: x ** 2)
    async with Runtime(
        squared.output,
        placement={squared: ProcessPlacement("compute")},
    ):
        return await squared.output.get(timeout=15)
```

继续保持以下语义：

- `Runtime(component.pose)` 只请求 pose；Component 根展开其公开输出，不自动请求写端口。
- `dependencies` 激活资源，不增加输出需求；`inputs` 与 command targets 形成明确的端口需求。
- `get()` 不隐式启动 provider、渲染器、远端订阅或改变 placement。
- `SharedComponent` 只连接；`SharedProvider` 才能在其所在环境创建 provider。
- `SampleId` 标识发布；`sequence` 是读端游标；两者均不等于文件标识或地图 revision。

### 3.2 可选的部署配置：提案 API

只在确有必要配置路径、启动超时或关闭策略时使用。默认调用不增加参数负担。

```python
# 提案：新增 rsim.runtime.options；定义与校验需在重构中实现。
from dataclasses import dataclass, field
from pathlib import Path

@dataclass(frozen=True)
class RuntimePaths:
    registry_root: Path | None = None
    storage_root: Path | None = None
    log_root: Path | None = None

@dataclass(frozen=True)
class ShutdownPolicy:
    grace_s: float = 5.0
    kill_wait_s: float = 5.0

@dataclass(frozen=True)
class RuntimeOptions:
    paths: RuntimePaths = field(default_factory=RuntimePaths)
    shutdown: ShutdownPolicy = field(default_factory=ShutdownPolicy)
    startup_timeout_s: float = 30.0
```

这些数值是建议初始配置，不是启动／停止耗时的实测保证。所有时长必须有限且为正数。

目标用法：

```python
# 提案 API；options 参数尚待实现。
options = RuntimeOptions(paths=RuntimePaths(log_root=Path("assets/runtime")))

async with Runtime(output, placement=placements, options=options) as runtime:
    report = runtime.diagnostics()
```

`SharedProvider(..., options=options)` 配置该 provider 自己的运行环境；`SharedComponent(..., options=...)` 只读取发现所需的本地设置，不得远程更改 provider 的路径或策略。

解析优先级统一为：显式参数 → 明确支持的环境变量 → 平台默认值。在 Runtime 打开前解析绝对路径，不依赖子进程当前目录。现有 `SharedProvider.log_path` 保留；与新配置重复指定时采用明确优先级或拒绝冲突，不静默忽略。

### 3.3 避免名字相同、角色不同的入口继续扩散

公共文档统一显式使用：

```python
from rsim.devices import Chassis                  # 连接已有控制服务
from rsim.drivers import Chassis as ChassisService # 装配／发布控制服务
from rsim.adapters.ros1 import Chassis as Ros1Chassis
```

当前根包 `rsim.Chassis` 指向 ROS1 adapter，而不是 `devices.Chassis`。本次**不能静默改指向**；保留兼容入口，更新文档与示例，并为未来弃用单独制定版本策略。[R9]

## 5. 平台内部 API：少量能力对象，不新增公共继承树

### 5.1 统一入口

`platforms.detect.get_platform()` 返回内部能力集合。它不负责启动 provider、推导端口或选择 ROS。

```python
# 提案：内部协议草案，不是可直接运行的实现。
from dataclasses import dataclass
from pathlib import Path
from typing import BinaryIO, Mapping, Protocol

@dataclass(frozen=True)
class HostIdentity:
    boot_id: str
    user_id: str
    platform: str

@dataclass(frozen=True)
class PlatformCapabilities:
    local_ipc: bool
    supervised_process: bool
    mapped_file_unlink: bool
    hardlink_reuse: bool
    managed_tree_cleanup: bool
    os_enforced_tree_containment: bool

@dataclass(frozen=True)
class ProcessSpec:
    argv: tuple[str, ...]
    cwd: Path
    env: Mapping[str, str]
    log_path: Path
    # 继承资源通过内部 BootstrapHandles 显式传入；不暴露裸 fd 给应用。

class ManagedProcess(Protocol):
    @property
    def pid(self) -> int: ...
    async def request_stop(self) -> None: ...
    async def wait(self, timeout: float | None = None) -> int: ...
    async def kill_tree(self) -> None: ...
    async def aclose(self) -> None: ...

class ProcessOps(Protocol):
    async def spawn(self, spec: ProcessSpec) -> ManagedProcess: ...

class SharedFileOps(Protocol):
    def open(self, path: Path, *, writable: bool = False,
             create: bool = False, delete_access: bool = False) -> BinaryIO: ...
    def hardlink(self, source: Path, target: Path) -> None: ...
    def unlink(self, path: Path, *, missing_ok: bool = True) -> None: ...
    def identity(self, file: BinaryIO) -> tuple[str, str]: ...
```

这些 Protocol 只描述内部替换边界。Linux 实现可以封装现有 `Popen`；Windows 实现可以封装现有 `JobProcess`。没有必要让用户注册平台插件。

`ManagedProcess.aclose()` 只释放句柄，**不会代替“是否应该停止 provider”的策略决定**。监督者仅在已经完成或放弃受管子树后释放其所有权句柄；客户端永不持有可关闭 provider Job 的句柄。

### 5.2 IPC、锁与租约的行为约定

| 接口组 | 最小行为 |
|---|---|
| `LocalIPC.listen/connect` | 返回受限本地字节流；平台层完成本地认证，上层处理 registry JSON |
| `LockOps.acquire` | 非阻塞或有期限等待；持有对象关闭后释放；区分占用与系统故障 |
| `LeasePair` | writer 正常关闭或所属进程死亡后，reader 能检测结束；非业务心跳 |
| `ShutdownReceiver` | 将 SIGTERM 或 Windows stop 请求转为相同的异步停止事件 |
| `SharedFileOps` | 支持协议所需的打开、映射后删除、同卷硬链接和文件身份检查 |

同一接口不必使用同一系统调用。不要将 Unix fd、Windows HANDLE、Job handle 或本地 endpoint token 放入公共 `Frame`。

### 5.3 能力检查

平台能力不能只由操作系统名称决定。选定目录可能不是 NTFS，DDS 库可能无法创建 participant，Notebook 也可能运行在不支持子进程的事件循环上。

**导入时不探测；在请求具体能力、正式打开资源前探测。** `doctor` 可以进行显式深度探测，包括子进程持有映射期间的删除／回读。标准 Runtime 使用缓存过的能力结果并处理实际操作失败。

Windows asyncio 的 subprocess 能力依赖事件循环，不能简单把任意 Notebook kernel 视为可用；失败信息应指向 loop 类型及独立 provider 的替代部署方式，不自动替换正在运行的 loop。[O3]

## 6. 生命周期：统一状态机，而不是统一退出信号

### 6.1 两种所有权策略必须保持分离

```text
ProcessPlacement
  Runtime ──私有 lease──> supervisor ──> worker tree
  Runtime 退出／死亡 → lease 结束 → 终止该 worker tree

SharedProvider
  launcher ──源 lease──┐
  client A ──源 lease──┼──> shared supervisor ──> provider tree
  client B ──源 lease──┘
  任一客户端离开只释放自己的 lease；最后一个 lease 结束才停止 provider
```

源租约、端口订阅、命令控制权是三个独立计数。退出一个地图查看器，不得撤销另一个控制器的控制会话；控制服务退出时，仍有图像读者的仿真源可以继续存在，但旧运动命令必须按其原有期限失效。

### 6.2 通用状态机

```text
NEW → STARTING → RUNNING → STOPPING → CLOSED
          │          │         │
          └──────────┴─────────┴──> FAILED（携带原始原因及清理结果）
```

启动是事务：验证环境 → 获得启动锁 → 建立私有目录与 lease → 创建 supervisor → 创建受管 worker → worker 完成初始化 → 发布 readiness。任一步失败均回收自己创建的资源，不删除其他实例的注册表。

PID 存在不等于 ready；readiness 必须在注册表可用、必要组件打开且实例身份确定之后发出。收到取消时既不能泄漏 worker，也不能吞掉 `CancelledError`。

关闭顺序：拒绝新写入／新订阅 → 撤销本会话控制权并执行 fallback → 停止任务 → 发送协作退出 → 等待 grace → 必要时终止受管树 → 关闭 IPC 与文件路径 → 记录清理结果。关闭动作必须幂等，并在有界时间内返回或抛出清理失败。

### 6.3 平台差异与保证范围

Windows 保留“挂起创建 → 加入 Job → 恢复执行”，避免 worker 在加入监督范围前运行。用于共享源的独立 supervisor 可以按策略脱离上层 Job；普通 worker 不得因为通用启动选项而自动脱离。仅继承白名单 HANDLE，Job 所有权句柄不得泄漏给子进程。Job 的终止与 breakaway 行为须按原生机制测试。[O1][O4]

Linux 保留进程组、私有 lease 和 exec trampoline。**`PR_SET_PDEATHSIG` 不是 Windows Job 的等价物，也不自动覆盖任意孙进程。** 本次默认保证 RSim 管理的 worker、受监督 native 进程和正常进程组；任意自行脱离监督的第三方 daemon 不在默认保证内。[R3][O5]

测试中须区分 `managed_tree_cleanup` 与 `os_enforced_tree_containment`。如产品要求对任意第三方后代提供更强的 Linux 隔离，需要另行提供 cgroup／服务管理器方案及验收，不能靠改名字宣称已有等价保证。

监督者必须独立于计算事件循环。渲染或数值计算阻塞时，源租约失效仍应触发回收。通用协程 deadman 不能被描述为实时硬件急停保障。

有界回收的强保证针对独立受监督进程。`LocalPlacement`／inprocess 中不响应的 native 调用或 Python 工作线程不能安全地被 Runtime 强制终止；需要可强制回收的物理／渲染任务必须放入受监督进程。不得在本地线程仍运行时报告“资源已经完整关闭”。关闭预算约束框架的等待与升级步骤，不是硬实时操作系统保证。

## 7. 注册表、目录与本地安全

### 7.1 运行目录分类

| 类别 | 生命周期 | Linux 默认目标 | Windows 默认目标 |
|---|---|---|---|
| registry | 当前 boot／用户范围 | 用户私有本地目录 | 用户私有本地目录 |
| payload | store／保留映射 | `/dev/shm` 下的私有目录 | 用户临时目录中的本地 NTFS 目录 |
| logs/report | 持久诊断 | 用户指定日志目录 | 用户指定日志目录 |
| scene cache | 仿真资产缓存 | adapter 配置 | adapter 配置 |

缓存和日志不随 payload 清理一起删除。库不应默认向安装目录或源代码目录写文件；apps 可以继续显式选择 `assets/`。

registry 路径由版本、boot、用户、domain 和逻辑 key 导出。物理设备锁另用与 domain 无关的设备身份；仅保护使用该锁协议的协作用户，不声称约束外部驱动。

### 7.2 Linux／Windows 同一用户边界

Linux 验证目录所有者与权限，拒绝不安全的符号链接；Windows 使用用户 SID 表示用户身份，并验证 endpoint record 的访问权限。仅把目录命名为用户名哈希，不足以证明目录私有。

Windows loopback listener 固定绑定本地地址，随机令牌不进入日志；endpoint record 原子写入。协议有限长，认证失败在派发 registry 请求前关闭连接。该令牌只保护本地控制通道，**不等于 DDS topic 已具备身份认证或加密**。

注册表失效后显式重新连接；不能仅因同 key 出现新 provider 就沿用旧实例的 SampleId、命令 token 或文件路径。

### 7.3 启动／最后退出竞争

同 key 的两个 launcher 与最后一个 lease 释放必须共享同一启动互斥规则。禁止出现“刚决定停止旧实例，另一客户端已连上却仍被清理”的窗口。

失败清理和陈旧文件回收必须核对实例身份，不能只按目录前缀、PID 或文件年龄批量删除。状态转换与文件删除分别记录，便于恢复未完成的清理。

## 8. 共享文件：保持行为一致，不承诺性能相同

### 8.1 必须保持的不变量

发布后的 payload 按不可变协议使用；新计算结果不能覆盖读者仍持有的旧数组。历史淘汰或 provider 关闭后，**已成功取得的映射继续可读**；尚未映射、已被淘汰的描述信息可以按 bounded/latest 语义跳过。

Linux 与 Windows 使用不同的文件打开／删除机制。Windows 必须对实际文件系统、句柄共享方式和映射生命周期做验证；不能仅依据系统版本推断所有 mapped-file 删除行为都可用。[R1][O2]

### 8.2 文件身份与逻辑身份分开

测试统一调用内部 `backing_identity(array)`，得到不透明的本机 backing 标识。Linux 可由设备号＋inode 表达；Windows 由卷标识＋文件 ID 表达。文件名相等、`id(array)` 相等或 `SampleId` 相等，都不能代替 backing 检查。

只在本机存储域内比较 backing。跨主机保留的语义身份是 SampleId，而不是 inode/file ID。多消费者测试应先确认读取的是同一个 SampleId，再比较 backing；两个异步 latest get 可能本来就拿到不同采样。

### 8.3 复用与复制的边界

| 情况 | 预期行为 |
|---|---|
| 同进程多个消费者 | 同一 Frame/payload 引用，不为组件边界创建共享文件 |
| 支持布局的同一活跃普通数组首次跨进程 | materialize 后复用 backing，避免按消费者数复制 |
| 完整只读映射，原路径有效且同一文件系统 | 允许硬链接复用 |
| 切片、非兼容布局、原路径已删除或跨卷 | 允许显式复制，并记录 copy reason |
| 晚订阅仍保留的普通 ndarray | 可以创建出口副本；不修改既有 Frame，不伪造一次源发布 |
| 未订阅大端口 | 不创建该端口 exporter／NPY payload；不保证源内部完全不计算它 |

不能把“同一对象复用”描述成“相同内容全局去重”。Windows 的磁盘后备映射也不能称为与 tmpfs 等速。

### 8.4 清理与容量

底层删除失败不静默吞掉。允许有界重试，但保留 `operation/path/error_code/instance_id` 诊断；清理只作用于属于本实例的资源。

显式监测已提交文件、materialization 字节数、复制原因、活动端口和清理失败。生产者 history 有界不代表进程总内存有界：应用长期保存 Frame，仍会持有对应映射。平台无法强制释放用户已保留的有效引用。

NPY 测试覆盖零长度、多维、非连续数组、字节序、结构化 dtype、Unicode 字段、只读标志与 Unicode／空格路径；object dtype 继续拒绝，不引入 pickle 解码。

## 9. 需求 API：将“是否需要采样”与“如何存储”分开

### 9.1 当前问题与目标

基线的 MuJoCo `_demanded()` 同时读取 Runtime 的 demanded ports 和 Signal 的 `_prepare_hooks`，用后者识别动态订阅。它把采样策略绑定到了 materialization 实现。[R4]

提案：Runtime 持有 `DemandTracker`；Signal 不增加资源生命周期；Component 仅提供只读查询。

```python
# 提案：添加到 Component 的轻量接口，不引入新的 Component 基类。
def has_demand(self, *port_names: str) -> bool: ...
def demand_snapshot(self) -> "DemandSnapshot": ...
```

`DemandSnapshot` 至少包含 generation 和该组件的 canonical port 集合。静态 roots/inputs、动态共享订阅与必要的内部消费分别持有 token；重复请求幂等，最后一个 token 释放才撤销对应需求。

声明接口、expose 别名和资源依赖不创建数据需求。内部算法若必需某个输入，必须显式声明，而不是依靠碰巧存在的 transport hook。

### 9.2 线程约定

MuJoCo worker thread 不直接读取会被 asyncio 修改的 Runtime 字典。事件循环中取得不可变快照，再传入物理／渲染线程：

```python
# 提案：MuJoCoSource 内部示意。
async def _tick(self):
    demand = self.demand_snapshot()
    async with self._access:
        packet = await self._work(self._advance, demand)
        await self._publish(packet)
```

0→1 需求变化触发下一次正常采样机会；1→0 只停止后续昂贵采样，不销毁仍在使用的物理世界，不释放其他端口。除业务明确要求外，不承诺订阅瞬间同步完成渲染。

这是**可选的生产者优化**。通用 Runtime 仍只负责传输裁剪；Mapping 的 pose 可能依赖完整建图状态，不能因 map 无订阅就自动关闭回环或地图算法。

## 10. 真机／仿真一致性：统一语义，不掩盖来源差异

### 10.1 先统一数据契约，再考虑更换 payload 类

本次优先在 `core/contracts.py` 中定义 TypedDict／校验函数与契约测试，保持现有字典编码可用。不要在平台迁移期间同时要求所有 IMU/Odom/Scan 改成新 wire 类型。

| 数据 | 必须规定的内容 |
|---|---|
| IMU | frame_id、xyzw 四元数、rad/s、m/s²、协方差、重力是否已扣除、字段不可用的表示 |
| Odometry/Pose | parent/child frame、米／弧度、速度所属坐标系、估计/真值、协方差语义 |
| LaserScan | 角度和扫描时序、量程单位、无回波约定、ranges/intensities 形状 |
| Image/Depth | shape/dtype/encoding、深度单位、光学 Z 或射线距离、无效值、camera_info 配对 |
| VelocityCommand | m/s、rad/s、机体坐标约定、许可、期限与 fallback |

字段值由来源决定，但含义必须一致。MuJoCo 提供的 `truth` 只能用于评估；验证轮速／IMU 控制链时应接 `PlanarOdometry(...).pose`，不以真值替代估计后宣称验证了定位算法。

### 10.2 设备是端口集合，而非新的万能基类

可新增轻量领域聚合值，供装配与测试使用；它没有自己的任务和进程，不要求继承 Component。

```python
# 提案：rsim.devices.ports 中的结构化端口集合。
from dataclasses import dataclass
from rsim.core import Signal, CommandSink, VelocityCommand

@dataclass(frozen=True)
class ChassisPorts:
    pose: Signal
    velocity: CommandSink[VelocityCommand]
    state: Signal
```

硬件、内存模拟和 MuJoCo 都提供这些端口，再交给同一个 controller/service。`devices.Chassis` 仍负责服务客户端，不与 `ChassisPorts` 合并。

### 10.3 三种时间不能混用

采样时间 `stamp_ns/clock` 用于同步；本机单调时钟用于命令 deadline；Unix `received_ns` 用于既有接收／诊断语义。远端和派生数据保留真实的新鲜度来源，不得用重复发布时的当前时间把旧反馈“刷新”。

仿真 speedup 改变推进速率，不改变真实控制租约按 host monotonic 失效的规则。暂停仿真后恢复，不得重新执行暂停前已经过期的命令。

重置时记录 episode/reset generation，估计器显式重置或重建 Runtime。即使为了 API 连续性保持 Signal 时间戳递增，也必须能区分重置前后的估计状态。

不同 host 的 monotonic 不直接相减；现有跨机控制保留保守的时钟换算，网络延迟消耗有效期，重试不得续期。命令时钟握手不替代传感器采样时钟同步。

### 10.4 物理与渲染所有权

保留 MuJoCo 的单 owner 工作线程，物理推进、渲染创建／使用／释放均串行。发布前从会被仿真下一步修改的内存生成稳定快照，不直接把活的 `MjData` view 作为不可变 Frame。[R4][O6]

`inspect(callback)` 与 `reset()` 保持仿真专用、进程本地工具接口；不能因为它们是 Python 方法就自动 RPC 化。需要远端 reset 时应另定义显式端口和状态重建协议。

## 11. 典型部署与使用方式

### 11.1 同一程序在两种 OS 上使用真实进程

第 3.1 节的 CounterArray/Map 示例作为最小平台回归：两个平台均必须产生不同 PID、正确结果、退出后无受管 worker 遗留。不得使用 inprocess 代替通过。

### 11.2 同一控制应用接真机与仿真

应用侧不导入 ROS、MuJoCo 或平台原语：

```python
# 使用现有公开接口；调用方先启动匹配的服务。
from rsim.devices import Chassis
from rsim import Runtime, TransportConfig

async def read_status(service_name="chassis", domain=42):
    client = Chassis(
        service_name,
        transport=TransportConfig(backend="cyclonedds", domain_id=domain),
    )
    async with Runtime(client):
        return await client.pose.get(timeout=10)
```

服务端分别选择：真实估计器＋硬件 sink，或仿真估计器＋MuJoCo sink。跨平台契约首先用零速、读取状态、退出与掉线验证；运动轨迹测试限定在模拟／受控实机测试环境。

本地算法单元测试可以显式选 `TransportConfig("inprocess")`；它仍是单事件循环的测试路径，不能作为跨环境 DDS 的证据。

### 11.3 Mapping：按需端口继续贯穿部署

```text
Linux ROS provider
  原生传感器 → LIO / 图优化 / MapLedger → pose | map | rgb_map | status
                                                │
                             同主机 SharedComponent / mmap
                                                │
                              ROS-free 应用／导航／记录器
```

```python
# 使用现有接口：只读取位姿与健康状态。
from rsim import Runtime
from rsim.devices import Mapper

async def observe_mapping():
    mapper = Mapper("mapping")
    async with Runtime(mapper.pose, mapper.status):
        pose = await mapper.pose.get(timeout=60)
        status = await mapper.status.get(timeout=10)
        return pose, status
```

验收重点：只请求 pose/status 时不产生 map/rgb_map 出口文件；两个 map 消费者复用支持的 backing；退出一个消费者不停止另一位；原子 map revision 与 SampleId 分别保留。

**上例不是 Windows 从 Linux 读取任意 Mapping mmap 的方式。** Windows 的 native mmap 与 Linux 的 tmpfs 分别只服务自己的 host。跨主机仍走已有 ROS2 topic 中继或明确的小消息服务；通用地图 payload 网络化不属于本次范围。

### 11.4 Windows MuJoCo：三个角色的生命期

```text
应用客户端（可独立 Python 环境）
  Chassis + SharedComponent 传感器视图
                │ DDS 小消息／描述信息
控制服务进程 ────┤
                │ 本机文件映射
物理 provider worker（独立 shared supervisor）
```

控制服务离开后，有传感器读者则物理 provider 保留；控制命令仍到期归零。最后一个源 lease 离开，才停止物理 worker 并清理路径。已拿到的 Frame 不因关闭服务而失效。

## 12. 错误、诊断与能力报告

### 12.1 统一错误分类

保留原有 `PortNotBound / ProviderDisconnected / CommandRejected / HistoryMiss`。平台内部错误向 Runtime 映射为可诊断的领域错误，而不是让用户直接处理 Win32 数字或特定 errno。

建议新增：`PlatformUnavailable`、`StartupFailed`、`CleanupFailed`。异常包含阶段、平台、实例、可公开路径与原始 cause；日志不包含 token 或 executable recipe。

必须区分：不支持该能力、必要依赖缺失、启动超时、provider 已退出、端口未绑定、控制请求被拒绝和清理失败。不可把“权限不足”报告为“设备正被占用”。

### 12.2 诊断 API 与命令：提案

```bash
# 提案：实现后用于部署与 CI；不是当前已提供的命令。
python -m rsim.apps.doctor --require process,shared-mapping --json
```

输出至少包含：系统与 Python、RSim 版本／commit、事件循环类型、DDS 端点探测、host/boot scope、文件系统能力、共享目录和日志目录、进程监督能力、渲染能力（显式请求时）。失败返回非零退出码。

`runtime.diagnostics()` 返回运行快照：active components、demanded ports、placement、worker 实例与 PID、活动源 lease／端口订阅数、失败与清理记录。报告结构可序列化，但不把内部可执行对象暴露出去。

启动日志应区分 `created / initializing / ready / failed`。崩溃报告与 worker 日志放在持久目录；payload 清理成功不能同时删掉唯一的故障依据。

## 13. 跨平台验收：同一份测试定义，两种真实实现

### 13.1 核心测试表

|---|---|---|
| P01 | LocalReference | 多读者共享引用；无 DDS、无共享文件副作用 |

同一测试通过 platform fixture 调用能力接口，而不是在行为断言中大量分叉。平台专属强保证另有测试：Windows Job owner 死亡回收普通孙进程；Linux 受管 lease 链和进程组回收。不要把未实现的强隔离功能用跳过掩盖后统一标为支持。

| ID | 验证项 | 内存模拟 | MuJoCo | 真实设备 |
|---|---|---|---|---|
| B01 | 端口类型、字段、SI 单位和坐标 | 必测 | 必测 | 必测 |
| B02 | 真值与估计来源明确 | 标记来源 | truth 与 odom 分离 | 不伪造 truth |
| B03 | 同一控制应用读取／零速／停止 | 必测 | 必测 | 独立安全环境 |
| B04 | stale feedback 不被心跳刷新 | 必测 | 必测 | 断开输入验证 |

| B06 | 渲染无需求不创建 Renderer | 不适用 | 必测 | 昂贵采样按能力验证 |

不得要求真机与 MuJoCo 的浮点结果、轨迹和调度时间逐位相等。相同接口不意味着使用相同噪声、摩擦、标定或动力学模型。

### 13.3 CI 和安装产物

建议在 `.github/workflows/` 增加以下职责明确的 job，而非单一“全部测试”命令：

| Job | 环境 | 发布门禁 |
|---|---|---|
| core | Linux＋Windows，最低支持 Python 与当前稳定 Python | 无 DDS/ROS 的核心、契约、inprocess、import guard |
| runtime-dds | Linux＋Windows，锁定 DDS 依赖组合 | P01–P25 中平台适用项；DDS 不可用应失败，不允许整组 importorskip 成功 |
| cross-python | 每个 OS 上两套指定 Python | 两个方向通信；记录解释器与 DDS 库版本 |
| mujoco-physics | Linux＋Windows | 生成场景、接触动力学、控制契约，无需图像测试 |
| mujoco-render | 已配置图形后端的 runner | RGBD、GL 线程关闭、晚订阅；不可由 physics job 替代 |
| ros2-integration | 指定 Linux ROS 环境 | ROS 数据转换、原生服务、relay、Mapping 装配 |
| hardware | 人工或专用安全 runner | 驱动停止、串口状态、控制最终行为；独立于普通 PR |

每个必测 job 输出 JUnit、平台诊断、依赖版本、跳过清单和失败日志。选定后端所需依赖缺失必须让该 job 失败；“全部被跳过”不是成功。

先 build wheel，再在临时干净环境中安装。测试可以从独立位置运行，但必须断言 `rsim.__file__` 指向安装产物，而不是工作区源码。不要依靠自动注入的源码 `PYTHONPATH` 掩盖打包遗漏。

## 14. 性能与资源验证

功能一致性和性能分别验收。至少记录 startup/first-frame、端口延迟 P50/P95/P99、命令确认、超时丢弃、映射建立次数、materialization 字节、磁盘 I/O、RSS、活动文件和句柄／fd、退出与回收时间。

负载包含：小消息、单路 RGBD、大点云、多个消费者、消费者晚加入、慢消费者、同时建图＋控制。每类 workload 固定尺寸、发布频率、history 和消费者数，并保存配置。

初版使用同平台基线比较，阈值写入测试配置；不规定 Windows 必须与 Linux tmpfs 同速。与安全相关的 deadline 不因性能不足而自动放宽；应隔离进程、减少无用订阅、降低非关键输出负载或明确拒绝控制。

控制停止测试同时记录“命令失效”“provider 输出 fallback”和“硬件反馈停止”，三者不是同一事件。软件测试不能替代实机最终制动验证。

## 15. 实施顺序与兼容迁移

| 阶段 | 改动范围 | 合并前验收 |
|---|---|---|
| PR0：基线固化 | 增加统一行为测试、诊断记录，保持布局不动 | 当前 Linux/Windows 各自的失败项与跳过项可复现 |
| PR1：原语下沉 | 新增 platforms；迁移 process/IPC/locks/files；旧函数薄转调 | P01/P02/P05/P06/P19/P21；已有公开导入不变 |
| PR2：监督状态机 | 共享启动事务、关闭顺序和两种所有权策略；保留 OS 原语差异 | P07–P14，包含强制结束、阻塞、取消与启动竞争 |
| PR3：独立需求状态 | DemandTracker、只读查询与线程快照；MuJoCo 不读 prepare hooks | P03、P04、B06；静态和晚订阅均正确 |
| PR4：数据一致性 | IMU/Odom/Scan 契约、fixture、truth/estimate 与时间规则 | B01–B08；现有字典 wire 不破坏 |
| PR5：发布门禁 | doctor、wheel 测试、双平台／双解释器 CI、迁移文档 | 必测 job 实际执行，日志和跳过清单完整 |

**不要在一个 PR 中同时移动文件、改变协议和更换所有数据模型。** 这样回归时才能判断是布局、平台实现还是业务契约出了问题。

兼容策略：

1. `Component / Signal / Runtime / ProcessPlacement / SharedProvider / SharedComponent` 现有调用保持。
2. `SharedSensor / ProcessSensor` 作为 legacy 入口保留，先接统一平台层，不要求业务同时迁移。
3. 保留现有 `python -m rsim.runtime.*` worker/supervisor 入口一段明确的过渡期，内部转调新实现。
4. 纯内部重排不升级 wire protocol；新增字段只有在兼容协商明确时使用，拒绝靠“另一端应当懂”假设。
5. 改变 registry record 或删除语义时先关闭旧实例；不得把旧运行目录直接交给不兼容的清理器。
6. 构造函数逐步收敛为验证与描述；参数文件、native 资源和目录的创建移至明确的 open／prepare 阶段，以免仅构图或序列化就写文件。
7. 每个阶段允许保留旧实现作为回退开发路径，但同一个运行实例只能由一种监督器拥有，不能同时双写 registry。

## 16. 完成标准

本次完成意味着：

- 同一份组件与控制应用不含 `sys.platform`、Win32、ROS 或 MuJoCo 条件分支。
- Linux/Windows 的平台分支集中在 platforms；runtime 统一生命周期策略，transport 保留数据格式职责。
- Windows 和 Linux 的真实多进程、独立解释器、保留映射和故障回收均有执行证据。
- 源租约、端口订阅、控制权独立；launcher 退出与 Runtime 退出的差异有测试。
- MuJoCo 的按需采样不再读取 materialization hook；跨线程只读快照的规则明确。
- 真值、估计、采样时钟、控制 deadline 和地图 revision 不混用。
- 通用 mmap 仍明确限于本机共享域；不存在宣称跨平台即可自动跨主机的接口。
- 平台能力不足、清理失败、依赖缺失和测试跳过均被显式报告。

最终保持以下模型：

```text
应用／算法：      Component → Signal / CommandSink
运行时策略：      Runtime → demand / placement / leases / supervision
通信与数据：      PortBinding → DDS／inprocess + SharedStore
操作系统机制：    Platform primitives → Linux 或 Windows
```

**平台迁移改变机制，不改变端口语义；真机与仿真改变数据来源，不改变控制应用；一致性由契约和测试证明，不由类名保证。**
