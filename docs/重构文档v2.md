# 重构文档v2

## SharedComponent 与端口级部署统一设计

**状态：重构提案，非现有 API 说明。**  
**范围：** 在现有 Component / Signal 架构上，统一独立环境共享与 Runtime placement 的端口绑定；以 Mapping 为贯穿案例。文中的新增接口均为设计草案，不应直接当作当前版本可运行代码。

> **统一的是端口契约与通道实现，不是进程的创建方式或生命周期。**  
> Component 决定计算和资源依赖；Signal / CommandSink 决定数据接口；Runtime 或共享 provider 决定这些接口如何跨边界。

---

## 1. 本次重构解决什么

保留已经建立的 `Component`、`Signal`、`Frame`、`CommandSink`、`ClockTransform`、`Synchronizer`。不再重新设计“Sensor 是否代表物理传感器”。现有核心已经区分资源依赖与数据输入，并将 Signal 的可用性归属于 producer。[S1]

本次只推进两个结构性变化：

| 变化 | 目标 |
| --- | --- |
| `SharedSensor` 的共享机制升级为多端口共享组件 | 独立 Python 环境之间直接连接命名 Signal / CommandSink，不再强制先合成一个 snapshot 再拆包 |
| placement 改为精确的端口需求规划 | 使用 `mapper.pose` 不隐式导出 `mapper.map`、`mapper.rgb_map`；指定进程位置不等于订阅全部输出 |

**边界约束：** 本次优先实现同一 Linux 主机、可共享注册表与存储空间的多进程／多 Python 环境。保留现有跨机小消息控制能力，但不把它等同于通用跨机图像、点云通道；通用 bulk 网络数据面另行实现。[S8]

## 2. 当前 Mapping 暴露出的两处问题

### 2.1 外部是多端口，内部共享仍是单输出

当前 `MappingOutput` 实际继承 `PrimaryComponent`，维护 `latest` 字典并发布聚合 snapshot；`MappingView` 读取该 snapshot，再把各成员发布到 `pose / odometry / rgb_map / map / status`。并不是 provider 内部已经有五个独立 Signal、只缺注册步骤。[S2]、[S3]

```text
当前：
原生建图输出 → MappingOutput.latest → 单输出 SharedSensor
                                      ↓ DDS 描述信息 + mmap
                               MappingView 拆包任务
                                      ↓
                         pose / odometry / rgb_map / map / status

目标：
Mapping Component 的命名输出
  pose ─────────────────────────→ 客户端 pose
  odometry ─────────────────────→ 客户端 odometry
  map ───── 仅存在订阅需求时 ────→ 客户端 map
  rgb_map ─ 仅存在订阅需求时 ────→ 客户端 rgb_map
```

目标不是消灭 `Bundle`：业务真正需要原子 snapshot 时仍可显式定义一个输出。要去掉的是**仅为了适配单输出共享通道而存在的聚合与拆包**。

### 2.2 placement 仍会扩大输出集合

当前 `BindingPlan.prepare()` 在处理部分跨位置输入、显式放置组件及跨位置资源依赖时，会把该 producer 的多个 outputs 一并加入导出集合。[S4]

因此，`Navigation(inputs=(mapper.pose,))` 可能引出不需要的地图通道。v2 要把“组件可达性”和“端口传输需求”分开计算。

## 3. 目标对象与职责

运行中的业务对象仍然只需要 Component 和端口。下面增加的是共享与部署支持对象，不要求算法继承新的复杂类型树。

| 对象 | 职责 | 不负责 |
| --- | --- | --- |
| `Component` | 计算、资源依赖、任务、失败；声明输入输出 | 决定 DDS topic、共享文件路径 |
| `Signal[T]` | 时间序列读取、有限历史、本地 sequence | 自己启动 producer 或创建进程 |
| `CommandSink[T]` | 写端口、命令校验和执行入口 | 充当反馈 Signal |
| `SharedComponent` | 客户端对已有共享组件的多端口代理 | 加载驱动工厂、启动另一解释器、复制计算图 |
| `SharedProvider` | 在提供者环境中承载组件、注册接口、维护租约和按需导出 | 将任意 Python 方法自动变成 RPC |
| `PortBinding` | 命名端口的导出、导入、codec、通道、错误传播 | 决定硬件由谁创建 |
| `BindingPlan` | 从根、输入及显式请求求端口需求，再按位置建立绑定 | 自动删减组件内部算法 |

`SharedComponent` 是逻辑组件的**本地代理**，不是第二个业务 producer。客户端仍可有本地 import 缓冲和本地 cursor；“去掉拆包重发布”不代表客户端不再需要解码和历史。

### 同一端口契约，不同生命周期

| 模式 | 另一侧如何启动 | 是否跨边界发送 Python 图 | 端口数据路径 |
| --- | --- | --- | --- |
| 同进程 | 当前 Runtime | 否 | 直接引用 |
| `ProcessPlacement` | 当前 Runtime 创建同环境 worker | 是，启动时的受信任代码／配置 | 同机端口绑定 |
| `SharedComponent` | 提供者在自己的环境显式启动 | 客户端不发送／接收工厂 | 复用同机端口绑定 |
| 未来跨主机 provider | 对端独立管理 | 否 | 显式网络端口绑定 |

`SharedSensor` 保留为单 primary output 的兼容入口；旧 factory 写法转交给提供者启动逻辑，不能再成为新多端口协议的基础类。`ProcessSensor` 同样保留兼容入口，但新代码优先使用 placement。

## 4. 端口级需求：先定义规则，再修改 planner

### 4.1 两个集合

Runtime 分别求解：

```text
ActiveComponents：需要运行／连接的组件
DemandedPorts：在哪些消费位置需要哪些端口
```

组件运行一次，不等于其全部输出都要传输。每条数据边保留消费位置：`(canonical_signal, destination_placement)`。

### 4.2 根与依赖规则

| 声明 | v2 语义 |
| --- | --- |
| `Runtime(mapper.pose)` | 激活必要组件；调用者位置只请求 pose |
| `Runtime(mapper.pose, mapper.status)` | 只请求两个输出 |
| `Runtime(mapper)` | 为兼容便利，调用者请求 mapper 全部公开输出；不自动获取控制权 |
| `Runtime(drive)` | 激活 Connect 及其依赖，请求实际输入和目标 sink；不扩张其他组件的输出 |
| `component.inputs=(mapper.pose,)` | 在该 component 的位置请求 pose；不请求 mapper 的兄弟端口 |
| `component.dependencies=(resource,)` | 激活资源；不因此订阅资源的全部输出 |
| `placement={mapper: ProcessPlacement("mapping")}` | 仅指定执行位置，不形成额外输出需求 |

只有**显式作为 Runtime 根的 Component**适用“全部公开输出”规则。经 inputs 或 dependencies 找到的组件不适用。

### 4.3 动态读取采用显式规则

第一版采用静态调用图规划：跨边界端口必须由根、inputs 或显式订阅声明请求。未绑定的远端端口 `get()` 报清晰的 `PortNotBound`，不得悄悄启动一个 producer 或订阅所有输出。

例如：

```python
# v2 目标语义；不是当前版本的端口裁剪保证。
async with Runtime(mapper.pose):
    pose = await mapper.pose.get()
    # mapper.map.get() 应提示未绑定，而不是隐式传入整张地图。

# 同时查看地图时显式声明。
async with Runtime(mapper.pose, mapper.map):
    pose = await mapper.pose.get()
    snapshot = await mapper.map.get()
```

同进程、已启动 producer 的其他本地输出可以直接读取；不要为了模仿远程限制给本地引用增加虚假传输。未来可增加显式动态 `subscribe()`，但不在 `get()` 中隐藏订阅副作用。

### 4.4 planner 流程

```text
1. 从 roots、inputs、dependencies、command targets 找到组件并做 canonicalization。
2. 校验 ownership DAG；数据反馈环仍由业务提供初值／延迟。
3. 确定 placement；process-local context 仍按进程建立。
4. 收集精确的读端口／写端口需求，并解析公开输出别名。
5. 同位置使用 LocalReference；仅为跨位置需求创建通道。
6. 同一 producer 端口共用 exporter；相同进程内兼容订阅共用 importer。
7. 启动／连接、安装绑定；退出时撤销本调用者的绑定与租约。
```

禁止再通过 `producer.outputs.values()` 自动扩张输入端口需求。允许在第 4 步对“显式 Component 根”展开公开输出。

**重要：这是传输裁剪，不是算法裁剪。** `mapper.pose` 可能依赖回环优化和地图状态；只读 pose 并不承诺 Super-LIO、RTAB-Map 或地图维护停止计算。若希望按需关闭建图分支，应拆为独立 Component 或增加算法自己的配置。

## 5. 多端口共享接口与发现

### 5.1 客户端与提供者分开

建议保留现有模块入口习惯：`rsim.devices.Mapper` 只连接，`rsim.drivers.Mapper` 组装／提供服务。通用运行机制由 runtime 实现。

下面是新增 API 的示意，不是完整类型定义：

```python
# 提供者环境：具备 ROS／算法依赖。
from rsim.runtime import SharedProvider, serve_shared

mapping = build_mapping_component(config)  # 返回多输出 Component
provider = SharedProvider(
    mapping,
    key="mapper:mapping",
    interface_version="mapping-ports-v1",
    provider_version=config_fingerprint,
)
await serve_shared(provider)
```

```python
# 应用环境：安装兼容的 RSim、DDS 和所用数据类型依赖，不加载 ROS。
from rsim.devices import Mapper
from rsim import Runtime

mapper = Mapper("mapping")  # 内部是带已知端口声明的 SharedComponent
async with Runtime(mapper.pose, mapper.status):
    pose = await mapper.pose.get(timeout=30)
    health = await mapper.status.get(timeout=5)
```

客户端工厂应能在连接之前构造逻辑端口，以便 planner 分析。SharedComponent 的 Runtime 可达性在代理处终止，不遍历 provider 私有计算图。运行时再把本地端口声明与 provider manifest 校验、绑定；未知的动态接口需先显式 describe，再建图。

### 5.2 注册表保存接口，不保存 Python 对象

manifest 示意：

```yaml
protocol_version: 2
component_key: mapper:mapping
instance_id: <每次 provider 启动生成的新 UUID>
interface_version: mapping-ports-v1
provider_version: <提供者配置指纹>
host_id: <主机标识>
domain_id: 0
ports:
  pose:
    direction: signal
    schema: rsim.pose.v1
    clock: <实际采样时间域>
    history_capacity: 64
  map:
    direction: signal
    schema: rsim.mapping-snapshot.v1
    clock: <实际采样时间域>
    history_capacity: 3
```

只读 Mapping 不声明写端口；底盘的 manifest 可另行声明 `velocity`，其 direction 为 sink，并注明命令 schema 和最大 TTL。声明端口只消耗元信息，不能因为 manifest 含 map 就创建 map exporter 或共享数组。

订阅应答再返回具体 `binding_id / channel_generation / topic / storage_descriptor / effective_history`。实例及通道代次隔离旧 DDS 描述信息，避免同 key 重启后误读旧帧。

### 5.3 身份与兼容性分开

`component_key` 解决“连接谁”；`instance_id` 区分该 key 的不同运行实例；`interface_version/schema` 决定线协议兼容；`provider_version` 校验竞争创建者的驱动／算法配置。客户端不需要知道数据库路径、日志配置和全部驱动参数。现有 `provider_version` 的职责可延续。[S5]

同机共享身份仍限定在同一可访问注册表／存储命名空间内，通常包括 host、Unix 用户、DDS domain 与 component key。物理设备的唯一性继续由**规范化设备标识和设备锁**保证，不由 DDS 名称或 Component Python 对象保证。

每个端口可以有不同 history。提供者历史、DDS 缓存和客户端历史是三种容量，不应继续作为同一个全局 `history` 强制相等。客户端时间查询默认只查本地已接收历史；要求更长历史可以协商或明确拒绝，不能伪装成远程历史已补齐。

## 6. 按需导出与租约：不能只把 snapshot 换成多个 topic

要实现“只用 pose，不共享 map”，必须同时约束客户端订阅和 provider exporter。

```text
提供者启动组件 → 公布 manifest，不为全部数据输出建立 exporter
客户端请求 pose → 校验接口与实例 → 取得源租约及 pose 订阅
首个跨边界订阅 → 启用一个 pose exporter → 返回绑定信息
其他订阅 pose → 复用 exporter，不重复运行 producer
最后一个 pose 订阅释放 → 停止该端口导出
最后一个源租约释放 → 按生命周期策略停止整个 provider
```

**源租约、端口订阅、写控制权分别计数／校验。** 订阅 pose 不获取 chassis 控制权；取消 map 订阅不关闭仍向其他人提供 pose 的 Mapping。

同机第一版可在现有注册表锁和 Unix socket lease 上扩充有限、版本化的 `describe / subscribe / unsubscribe` 管理协议。数据描述信息仍走 DDS，数组仍走 mmap；无需为了复用端口模型把本机租约改为 DDS 分布式锁。

管理请求需要幂等 ID；创建／销毁 exporter 在提供者侧串行化。断开连接释放该会话的全部订阅。首次订阅完成后提供一份仍保留的最新样本或等待下一样本；不承诺完整历史回放。重新创建通道时必须使用新代次，不能复用序号而接受旧缓存。

SharedProvider 应在**已有运行图**中挂接出口，不通过为每个端口创建 `Runtime(producer)` 来导出，否则会导致生命周期冲突或重复启动。

provider 启动者自身持有一个源租约；启动者离开而其他客户端仍持有租约时，受监督 worker 继续运行。普通 `ProcessPlacement` 则仍跟随所属 Runtime。只有控制 provider 的明确管理者可以强制关闭整个服务。

## 7. 统一 PortBinding 与物理数据共享

### 7.1 复用同一套出口／入口

从 `runtime/deployment.py` 提取可复用的端口绑定实现，使本地部署计划和共享服务都调用它：

```text
ProcessPlacement ──┐
                   ├── PortBinding ── Signal exporter/importer ── DDS + SharedStore
SharedProvider ────┘               └─ Command client/server ─── 最终 sink 校验
```

绑定应以 canonical port 和位置为键，而不是以“哪个客户端发起连接”为键。一个共享代理被放入计算 worker，只是在 worker 内建立客户端连接；不会把原 provider 的驱动图复制进去。

Signal 的材料化策略通过 runtime/binding 注入，Signal 核心不导入 transport。共享 provider 内部也使用 ProcessPlacement 时，应解析到实际 producer 位置复用出口；不能先把所有数据导回主进程，再为每个客户端重新导出。导出回调必须支持引用计数：一个订阅结束不能清除其他有效订阅需要的材料化策略。

### 7.2 物理唯一性的精确定义

同进程扇出复用 Frame／payload 引用；跨进程时，同一不可变数组的同一材料化结果可供多个 reader 映射。完整共享数组在后端支持、原路径有效时可继续复用；切片、重新排布、主动复制、已失去可重开路径后的重导出不承诺零复制。现有 SharedStore 的这些边界应保留。[S1]、[S7]

“只材料化一次”不是全局内容去重，也不表示源头永远只有一份内存：首次共享时原始生产缓冲可能仍存在。材料化缓存至少区分发布／payload 身份；不同对象仅因数值相同不得自动当作同一数据。

动态挂接已有 Signal 时，不得修改已交给消费者的 Frame，或重新发布旧数据来制造新 sequence。可为保留的样本建立出口缓存，再处理新发布。`get()` 后长期保留 Frame 仍会保留页映射，有限 history 不等于总内存固定上限。

### 7.3 不把 allocate() 变成隐藏的强制共享

现有代码允许主动调用共享 allocator。若 Mapping 工厂无条件给内部所有算法注入共享 allocator，即使 planner 不导出 map，也仍可能产生共享文件。

因此 v2 默认内部计算使用普通分配；只有边界材料化或算法明确选择的共享输出使用共享 allocator。验收分别记录“算法主动共享分配”和“通道自动材料化”，不能把减少 DDS topic 当作没有共享内存开销。

## 8. Mapping 案例：逻辑图与多输出

当前 Mapping 已集成激光惯性估计、RGB 上色、可选轮式／扫描融合、回环优化与带来源信息的地图；以下用这些功能说明目标结构，不要求把全部原生算法改写成 Python。[S6]

```text
规范化后的 lidar ──┐
                   ├── LIO ── scan_state{去畸变点云, 同时刻位姿}
IMU 时间窗口 ──────┘       └─ 高频 pose_history

RGB + 标定 ───────────────────────────┐
scan_state + pose_history ────────────┼── RGB 投影／运动补偿 ── keyframe
                                     │
wheel odom + gyro + scan odom ── 可选局部融合 ── local_odometry

keyframe + local_odometry ── PoseGraph／RTAB-Map ── optimized_keyframes
不可变关键帧观测 + optimized_keyframes ── MapLedger ── map / rgb_map

局部位姿 + 全局修正 ── pose
各阶段诊断 ── status
```

未启用局部融合时，LIO 提供局部 odometry。`scan_state` 有意把扫描与对应位姿作为一个关联样本：不能把“原子一致的算法输出”误拆成两个互不关联的 topic。

### 8.1 组装接口

下面的 `MappingPipeline`、`SignalRosInputs`、`expose()` 均为目标接口示意：

```python
class MappingPipeline(Component):
    def __init__(self, *, rgb, lidar, imu, odom, calibration):
        # 原生 ROS 算法可继续作为一个内部集成单元存在。
        ingress = SignalRosInputs(
            rgb=rgb, lidar=lidar, imu=imu, odom=odom,
            calibration=calibration,
        )
        backend = NativeMappingBackend(ingress)
        super().__init__(backend, inputs=(rgb, lidar, imu, odom))

        # 公开内部已有输出，不再创建轮询拆包任务。
        self.pose = self.expose("pose", backend.pose)
        self.odometry = self.expose("odometry", backend.odometry)
        self.map = self.expose("map", backend.map)
        self.rgb_map = self.expose("rgb_map", backend.rgb_map)
        self.status = self.expose("status", backend.status)
```

`expose()` 应成为受支持的别名接口：保留实际 producer、样本身份和缓冲，不复制计算，也不创建第二个发布任务；仍传播外层组件关闭／失败。planner 必须沿别名找到真实端口。

第一阶段可以不引入 `SignalRosInputs`：保留现有 `mapping_graph()` 的原生集成结构，先把 `MappingOutput` 改为真实多输出并接入共享协议。之后再按复用需求拆分内部阶段。

### 8.2 不重复采集原始设备

如果 Mapping 和其他组件都需要相机／雷达，提供者应复用已有设备源的端口，而不是各自在自己的子图中再次启动同一驱动。

设备锁只能“拒绝第二次占用”，不能自动把两套采集代码变成共享。需要在组装层明确选择：由 Mapping 独占管理原始设备，或由独立设备 provider 管理并向 Mapping 提供 Signals。未知外参、时钟关系和不同驱动配置不能因设备 key 相同而静默复用。

## 9. Mapping 案例：三种部署不改变端口语义

### 9.1 同环境分进程

```python
# 目标示例：相关 adapter 必须能在所选解释器内运行。
mapper = MappingPipeline(
    rgb=camera.image, lidar=lidar.points,
    imu=imu.data, odom=chassis.odom, calibration=calibration,
)
nav = Navigation(pose=mapper.pose, obstacles=local_cloud, goal=goal)

async with Runtime(nav.command, mapper.status, placement={
    mapper: ProcessPlacement("mapping"),
    nav: ProcessPlacement("navigation"),
}):
    command = await nav.command.get()
```

mapper 的 ownership 依赖可跟随 mapper；Signal 输入仍保留各自位置。边界只导出实际使用的输入，以及 `pose / status`；不因显式放置 mapper 就导出 `map / rgb_map`。这里不连接真实执行器。

### 9.2 独立 ROS 环境提供完整 Mapping

```text
ROS／算法环境                         AI／应用环境
设备适配 + 原生 Mapping                SharedComponent("mapper:mapping")
    pose ───────── DDS 描述信息 ─────────────→ Navigation / UI
    status ─────────────────────────────────→ 诊断
    map ── 只有地图消费者存在才启用 ────────→ 地图应用
                    同主机数组使用 mmap
```

这是迁移当前 Mapper 的最小路径。应用端不加载 rclpy；提供者内部需要 ROS 的代码仍在 ROS 环境运行。客户端 Python 可以不同，但各端数据 schema、codec 及实际使用的数据类型依赖必须兼容。不能只因都是 Python 就认为任意对象可跨环境传递。

### 9.3 设备 provider 与算法环境继续分开

硬件 provider 可以只提供 `image / points / imu / odom`；另一环境连接这些端口后组装自己的 Mapping，再通过 placement 分配计算。

这不会让基于 ROS 的原生 wrapper 自动变成无 ROS 算法：若 Mapping 仍需启动 ROS 节点，其所在环境必须具备对应依赖，或将那部分封装为独立 provider。

通用跨主机大数组仍不是本次交付。未来远端接收侧可缓存一次 payload，再供本机多消费者共享；不同主机有不同物理副本，以样本身份关联，不以 inode 相等定义全局唯一。

## 10. 时间、样本身份与地图版本：三种不同一致性

### 10.1 时间同步不能退化成全局大 Bundle

保留 `Frame.stamp_ns / clock / received_ns` 与显式 `ClockTransform`。`clock` 是时间域，**不是**地图坐标系；`frame_id`、Pose 的坐标标签与 `map_revision` 是另外的概念。[S1]

Mapping 采用局部同步策略：LIO 需要覆盖扫描区间的 IMU 序列，RGB 上色需要图像、扫描及可插值位姿历史，导航需要有新鲜度上限的 pose／障碍物，目标可以是持续有效的状态。不要为所有输入强制采用同一个最近邻 join。

现有 `Synchronizer` 适合容差内最近邻／显式插值；不能把它当作无损 IMU 批处理器。积分和去畸变所需窗口应由算法入口保留并检查覆盖、缺样、乱序与超时；latest-value `get(after=...)` 允许跳帧。[S1]

运输不重写采样时间来伪装同步。接收时间估计的偏移必须标明精度边界；不同主机的 monotonic clock 不能直接相减。跨机时钟身份还应包含主机／时钟实例范围，不能仅凭同名 `host:monotonic` 判为同域。

### 10.2 引入可跨端口绑定保留的 SampleId

保留 `Frame.sequence` 为本地 cursor，同时为新协议增加：

```text
SampleId = (producer_instance_id, canonical_port_id, publication_sequence)
```

为 Frame 增加向后兼容的可选 `sample_id` 字段；旧来源可为 None，新协议的出口必须提供稳定身份。同一个历史样本退订后重新导出，仍使用原 SampleId；端口通道重建不等于重新采样。导入、别名和纯运输转发保留原 SampleId；真正的计算输出创建新 SampleId。Derived output 的来源关系按需记录，不把输入 SampleId 冒充输出身份。

provider 重启产生新 instance；关闭后重开的本地 producer 也必须有新的实例代次。不能用 `sequence`、时间戳或文件路径单独代替全局样本身份。

Mapping 内部已有 `(session_id, source_id)` 表示激光观测来源。[S6] 这是**领域观测身份**，不等于某次 map Signal 发布的 SampleId；回环后同一批观测可出现在新的地图发布中。

### 10.3 拆开端口，不拆坏原子地图

独立的 pose、map、rgb_map topic 不保证同时到达，连续两次 `get()` 也不保证同一优化版本。每个地图快照保留原子 `(session_id, revision)`；与地图相关的 pose／rgb_map 应携带对应版本上下文，可通过明确的 Frame metadata 或领域 envelope 表达并纳入 schema。

消费者需要同版本数据时显式检查 revision；需要一次原子读取时，定义业务输出 `mapping_snapshot`。不要为了原子性又强制所有客户端订阅它。时间对齐与版本匹配必须分别校验。

## 11. 多消费者、多控制者与失败边界

### 11.1 多消费者

```text
                 ┌─ Navigation 只订阅 pose
Mapping.pose ────┼─ UI 只订阅 pose + status
                 └─ Recorder 订阅 pose
Mapping.map ─────── 地图应用订阅 map
```

一个 Mapping producer；每个有跨边界需求的端口一个有效出口，多 reader 共享不可变 backing。地图应用退出后释放 map 出口，不能中断导航。Recorders 采用 latest 接口时仍可能丢帧；无损记录必须另设传输和背压策略。

### 11.2 多控一

```text
Navigation.command ─┐
Manual.command ─────┼── CommandMux ── Connect ── Chassis.velocity
                    └─ 优先级／超时／手动覆盖
```

SharedComponent 暴露 sink 不表示多个客户端可自由竞争。保留 Runtime 的写入者检查，并在最终 provider 保留独占会话、epoch、sequence、deadline 与 deadman 校验；只读连接不获取控制权。[S1]

跨环境请求必须绑定目标 provider instance，防止重启后旧指令被误用。重试与转发不续期；原有 envelope 的 deadline 保持有效期语义。跨主机由已定义的时钟换算协议处理，不能原样比较双方 monotonic 值。

停止与过期保护应在硬件附近执行，不能只依赖应用清理；软件 CommandMux 不是硬件急停替代品。请求收到／接受也不等于电机已经执行。

### 11.3 生命周期与故障

Signal 不新增自己的 open/close，但绑定有管理生命周期。发生 provider 退出、实例变化或通道错误时，唤醒对应等待者；依赖传播仍由 Runtime 处理。

默认遇到 provider 实例变化应明确报错并要求重建／重新绑定，尤其写端口不得无提示恢复控制。端口故障不必立刻杀死健康的整个 provider；组件自身失败、存储故障和特定端口错误应能够区分。取消订阅后的旧 mmap 可以继续读，但不能继续 `get()` 假装 producer 正常。

## 12. 迁移落点与顺序

| 阶段 | 修改位置 | 完成标志 |
| --- | --- | --- |
| A. 精确需求计划 | `runtime/graph.py`、`runtime/deployment.py` | 区分激活组件与被请求端口；显式 placement 不扩张 outputs；调整依赖旧行为的测试 |
| B. 端口绑定提取 | 从 deployment 提取 runtime 内共享 binding 逻辑；复用 `transport/commands.py`、`transport/shared.py` | ProcessPlacement 先通过同一套 exporter/importer 和错误处理回归 |
| C. 多端口共享 | `runtime/host.py` 相关 provider／client；新增 manifest、管理协议和订阅计数 | 跨环境连接不交换工厂；只请求所需端口；旧 SharedSensor 进入兼容层 |
| D. Mapping 迁移 | `adapters/ros2/mapping_output.py`、`drivers/mapping.py`、`devices/mapping.py` | provider 直接发布命名 Signals；删除仅为共享而存在的 snapshot 拆包循环；保留客户端本地 save |
| E. 身份与一致性 | `core/model.py`、端口 codec、Mapping schema | SampleId 穿透转发；地图 revision 可校验；协议升级明确 |

新增实现应放在现有包层级内：core 只存契约和纯元信息；runtime 管注册、租约、需求计划与绑定生命周期；transport 管消息和存储；drivers 管组装；devices 管无 ROS 客户端视图。无需为此引入插件框架或远程 Python 对象系统。

对现有小消息控制服务先维持兼容，不要顺带重写为新的泛用 RPC。新多端口协议使用明确版本；旧 provider 不支持时应报不兼容，或由显式 legacy adapter 接入，不能默默退回“大 snapshot”并宣称满足按需导出。

## 13. 验收用例

测试应检查通道／材料化计数与实例身份，而不只检查最终数值相等。

| 用例 | 必须满足 |
| --- | --- |
| `Runtime(mapper.pose)`，mapper 在 worker | 只建立 pose 所需边界通道；不因该请求创建 map／rgb_map exporter 或触发其边界材料化 |
| 同一 mapper 输出 pose、map、内部 debug | 仅外部需要的输出跨边界；未暴露内部 debug 保持本地 |
| 多客户端、多端口 | 所有客户端指向同一 provider instance；相同端口共用 exporter；不同端口订阅独立增减 |
| 同数组多路扇出 | 受支持路径中映射到同一文件 backing，可用有效生命周期内的 `(st_dev, st_ino)` 核对；不依赖 Python `is` 跨进程判断 |
| 同图改变 placement | 数据及时间语义保持；算法不因消费者增加而重复启动；只有存储类型／传输边界可变化 |
| 应用与提供者解释器不同 | 应用和其计算 worker 禁止导入 ROS；未交换 provider 工厂；值按 schema 解码 |
| 只取 pose 的共享客户端 | provider 端也不提前创建地图出口；验证不是仅少建一个 DataReader |
| 订阅／取消并发、客户端崩溃 | 不出现双 exporter、失效租约或错误关闭仍被使用的 provider；全部退出后回收资源 |
| 退订后再次订阅、provider 重启 | 正确处理 channel generation／instance；不接受旧缓存或旧控制指令 |
| 不同 clock／IMU 窗口缺样 | 未配置映射时报错；窗口不足按算法策略拒绝／降级，不能用 latest 样本冒充完整窗口 |
| 回环更新期间读取 pose 与 map | 检测不同 revision；原子地图快照内部所有数组版本一致，来源特征不丢失 |
| 多 writer、过期、重放、断联 | 最终 provider 拒绝无效命令；Mux 仲裁显式；过期保护与应用是否存活解耦 |

**关键验收界限：** pose-only 用例证明的是“没有不必要的地图传输／边界共享”，不是“建图算法不分配地图内存”。算法主动共享分配和后台地图计算需独立记录。

## 14. 本次不做的事情

不自动远程化任意 `save()`、`reset()`、service 或 Python 属性；只读导出可继续在客户端实现，远程操作必须另行声明协议。不要把 `CommandSink.set()` 扩展成任意长任务 RPC。

不自动选择跨 Python ABI 的解释器、迁移活动对象或在线搬迁算法。ProcessPlacement 是同环境部署；独立环境通过已启动的 provider 连接。

不承诺全局无损流、硬实时、全链路零拷贝、任意多机大数组共享，也不把 DDS domain／key 当作认证。共享服务的信任范围与网络访问控制必须独立说明。

**最终结果：同一张 Component / Signal 图，无论通过当前 Runtime 部署，还是连接独立环境的 provider，都沿同一套命名端口契约绑定；只传所需端口，不重复 producer，不为传输而扭曲业务数据模型。**
