# PTP 时钟同步与建图

PTP 对齐设备采样时钟，使雷达逐点时间可以与其他传感器的时间比较。它不减少 DDS 传输延迟，也不替代外参标定、位姿融合或回环优化。

## 主机作为时间源

对于直连雷达、支持硬件时间戳的网卡，常见同步方向是：

```text
NTP → 主机 CLOCK_REALTIME（UTC）→ 网卡 PHC（PTP 时间）→ 雷达
```

`ptp4l` 在物理网口运行，网口即使属于网桥也应使用实际具有 PHC 的端口。`phc2sys -s CLOCK_REALTIME -c <interface> -w` 将主机时间同步到该网卡，并从 `ptp4l` 取得 UTC/PTP 偏移。不要同时让另一个服务反向调整系统时钟，否则可能与已有 NTP 服务相互干扰。独立的 PTP 管理 socket 需要给两者配置相同地址。

守护进程适合交给系统服务管理，保证未登录时也能启动；网络接口、配置路径和 domain 放在部署参数中，不写进传感器代码。配置依赖和异常重启时，应确保 `ptp4l` 重启后 `phc2sys` 也能重新连接，且每个硬件时钟只有一个调节进程。

## 建图时间尺度

先读取 PTP 时间属性和设备同步状态，再检查真实点云的逐点时间。`ptp4l` 显示 MASTER 只说明本机角色，不能证明雷达已经锁定。还要检查雷达自身的 LOCKED 状态、同步偏移，以及源时间是否持续前进。

ROS system 时间采用 Unix/UTC 语义，而硬件时间戳 PTP 通常使用连续的 PTP/TAI 时间尺度。设备驱动可能已转换为 UTC，也可能原样发布 PTP 时间。读取当前 `currentUtcOffset`，核实点时间与主机时间的关系后，再配置：

```python
# 设备原样发布 PTP 时间时：
timing = {
    "lidar": {"offset_s": -current_utc_offset},
    "chassis": {"offset_s": measured_chassis_offset},
}
```

若设备已输出 UTC，雷达偏移应为零；不能再次扣除 UTC/PTP 差值。`current_utc_offset` 与底盘偏移由部署测量提供，不是固定在库内的常量。闰秒或设备时间模式发生变化时，应重新核实并启动新的建图会话。

只同步雷达不会自动同步远端底盘、USB 相机或串口 IMU。各源必须分别确认时钟语义；尚未同步的底盘可继续显式采用接收时刻估计，但其传输延迟和漂移仍影响融合。建图可以等待迟到数据并按采样时间插值，无需把时间戳改成接收时刻。

## 验收边界

- 启动前等待网卡时钟收敛和雷达锁定；服务 active 不等于同步完成。
- 检查转换后的扫描结束时刻与接收时刻之差。这个值包含采样、驱动和传输延迟，不能将它直接当作 PTP 同步误差。
- 确认逐点时间跨度、扫描间隔与相对点时间保持不变，时间回退不能静默拼接到旧会话。
- 记录失锁和系统时间跳变；失锁后的保持时间不能视为持续受同步约束。现有标准 PointCloud2 不携带厂商 PTP 锁定状态，RSim 的固定偏移也不会自动监测该状态，部署时需独立监测。
- 静态采集可验证时间尺度、输入配对和地图输出；要量化运动去畸变与建图精度的改善，仍需相同路径的动态对照或外部真值。
